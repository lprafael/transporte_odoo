OPCIÓN A Transmisión vía API REST (HTTP POST)

Recomendado para pruebas inmediatas desde plataformas de rastreo en la nube (Sitrack, Megat, Skycop, EPAS, Hunter, etc.), gateways webhooks, o módems celulares programables con soporte HTTP.

Parámetro Valor Exacto Detalle / Requisito
URL Endpoint Principal http://192.168.1.100:8088/api/v1/telemetry Alias admitido: /telemetry/gps
Método HTTP POST Cuerpo de la petición en JSON UTF-8
Header Autenticación X-Device-Token: GPS_DEVICE_SECRET_2026 Obligatorio (HTTP 401 si falta)
Header Formato Content-Type: application/json Obligatorio
Frecuencia Recomendada Cada 10 segundos (ó cada 5 a 15 seg) Estándar oficial de telemetría urbana

1. Estructura del Payload JSON

payload_telemetria.json 
{
  "mean_id": "00016",                // N° de Interno / Móvil oficial (Obligatorio, ej: "00016" o "104")
  "license_plate": "AARX 104",       // Chapa / Matrícula Mercosur (Opcional)
  "agency_id": "004B",             // Código de la empresa titular (Obligatorio: "004B")
  "route_id": "020c",              // Código del ramal activo (Obligatorio: "020c", "020d", etc.)
  "driver_id": "4589123",          // Cédula / Legajo del conductor (Opcional)
  "latitude": -25.334120,          // Latitud WGS84 decimal (Obligatorio, no enviar 0.0)
  "longitude": -57.521450,         // Longitud WGS84 decimal (Obligatorio, no enviar 0.0)
  "velocidad": 38.5,               // Velocidad instantánea en km/h
  "rumbo": 295.0,                  // Dirección en grados (0° a 360°, hacia dónde apunta el frente)
  "odometer_km": 48230.5,          // Kilometraje acumulado en odómetro
  "precision": 8,                  // Margen de error satelital en metros (≤ 50m)
  "altitud": 124.0,                // Altitud sobre nivel del mar en metros (Opcional)
  "fecha_hora": "2026-10-09T10:15:30Z", // Timestamp UTC satelital formato ISO-8601
  "type": 2                        // 0=INICIADO (Salida), 2=OPERANDO (En ruta), 1=FINALIZADO (Llegada)
}

OPCIÓN B Transmisión vía Broker MQTT (Res. GVMT 065/2024)

Para módems de telemetría vehicular (4G/LTE CAT-M1) que transmiten nativamente por MQTT. Cumple de forma estricta con las especificaciones del Viceministerio de Transporte (Paraguay).

Parámetro MQTT Valor de Configuración Descripción
Host / Broker 192.168.1.100 IP o dominio del servidor de telemetría
Puerto MQTT TCP 1883 Puerto Mosquitto estándar sin SSL / TCP plano
Puerto WebSockets 9001 Puerto alternativo WebSockets
Usuario MQTT gps_device Usuario asignado a la flota
Contraseña MQTT GPS_DEVICE_SECRET_2026 Clave de acceso vehicular
Tópico Oficial de Publicación transporte/flota/004B/operacion Patrón general: transporte/flota/{agency_id}/operacion
Calidad de Servicio (QoS) QoS 1 At least once (Garantiza entrega contra cortes celulares)
Carga Útil (Payload) Dual: Protobuf v3 binario ó JSON plano El broker detecta el formato automáticamente
💡
Reconocimiento Automático de Payload:
Si su equipo envía la trama binaria compilada con transit.proto (mensaje Operation), el broker la decodifica de forma nativa. Si su módem o plataforma prefiere enviar un string JSON al tópico MQTT, el broker lo detecta y procesa con exactamente el mismo resultado.

Script de Prueba en Python (Publicador MQTT)

test_mqtt_publisher.py 
# Requiere: pip install paho-mqtt
import time
import json
import paho.mqtt.client as mqtt

BROKER_HOST = "192.168.1.100"
BROKER_PORT = 1883
USERNAME = "gps_device"
PASSWORD = "GPS_DEVICE_SECRET_2026"
TOPIC = "transporte/flota/004B/operacion"

client = mqtt.Client(client_id="test_gps_device_00016")
client.username_pw_set(USERNAME, PASSWORD)
client.connect(BROKER_HOST, BROKER_PORT, 60)
client.loop_start()

payload = {
    "agency_id": "004B",
    "mean_id": "00016",
    "route_id": "020c",
    "driver_id": "4589123",
    "latitude": -25.33412,
    "longitude": -57.52145,
    "velocidad": 35.0,
    "rumbo": 290.0,
    "odometer_km": 48230.5,
    "type": 2  # 2 = OPERANDO
}

print(f"Enviando ping MQTT a {TOPIC}...")
client.publish(TOPIC, json.dumps(payload), qos=1)
time.sleep(1)
client.disconnect()
print("¡Ping entregado exitosamente!")

CATÁLOGO Ramales Oficiales para E1, E2 y E3

El campo route_id en cada ping debe configurarse con uno de los códigos de ramal oficiales para que el motor geoespacial calcule el avance del itinerario, la geocerca de salida/llegada y el desvío de la traza:

Servicio Código route_id Nombre y Descripción Oficial Sentido Distancia Salidas Prog.
E1 020c Ramal 020C - San Lorenzo a Asunción Centro Ida 19.46 km 110 salidas
E1 020d Ramal 020D - Asunción Centro a San Lorenzo Vuelta 19.78 km 110 salidas
E2 020e Ramal 020E - San Lorenzo a Asunción Variante Ida 19.53 km 150 salidas
E2 020f Ramal 020F - Asunción Variante a San Lorenzo Vuelta 19.82 km 150 salidas
E3 0210 Ramal 0210 - Luque (Aeropuerto) a Asunción Ida 18.33 km 86 salidas
E3 0211 Ramal 0211 - Asunción a Luque (Aeropuerto) Vuelta 18.84 km 86 salidas
Taller 0000 Sin Ramal / En Depósito o Taller Mecánico N/A 0.00 km 0 salidas
📌
Identificador del Bus (mean_id):
En el sistema ERP Odoo y en el VMT, los buses eléctricos están empadronados con códigos correlativos (ej: 00016, 00017, etc.) y números de interno (ej: 104, 105). El receptor acepta indistintamente el código de 5 dígitos o el interno numérico.

DICCIONARIO Campos del Protocolo & Archivo Protobuf

A continuación se detalla el esquema formal transit.proto estandarizado según la Resolución GVMT N° 065/2024:

transit.proto 
syntax = "proto3";

package transit.telemetry;

import "google/protobuf/timestamp.proto";

message Operation {
  enum OperationType {
    INICIADO = 0;    // Salida de cabecera / inicio de jornada
    FINALIZADO = 1;  // Llegada a terminal / fin de servicio
    OPERANDO = 2;    // Coordenada periódica en ruta (cada 10 seg)
    SUSPENDIDO = 3;  // Servicio interrumpido / auxilio mecánico
  }

  // --- Campos Requeridos ---
  int32 identidad = 1;                     // ID de la entidad emisora
  string agency_id = 2;                    // Código de empresa (ej: "004B")
  string mean_id = 3;                      // N° de bus / interno (ej: "00016")
  string route_id = 4;                     // Código del ramal (ej: "020c")
  string driver_id = 5;                    // Documento / legajo del conductor
  OperationType type = 6;                  // Tipo de evento operativo (0, 1, 2, 3)
  int32 accuracy = 7;                      // Precisión GPS en metros (≤ 50)
  double latitude = 8;                     // Latitud WGS84 decimal
  double longitude = 9;                    // Longitud WGS84 decimal
  google.protobuf.Timestamp datetime = 13; // Fecha y hora UTC del satélite

  // --- Campos Opcionales ---
  double altitude = 10;                    // Altitud sobre el nivel del mar (m)
  double bearing = 11;                     // Rumbo en grados (0° a 360°)
  double speed = 12;                       // Velocidad del móvil en km/h
}

Reglas de Negocio y Validación Automática

Validación Criterio Aplicado Acción del Receptor
Coordenadas Cero / Inválidas lat == 0.0 AND lon == 0.0 o fuera de [-90, 90], [-180, 180] Descarte Inmediato (Se ignora para no ensuciar auditorías)
Exceso de Velocidad velocidad > 70.0 km/h Alerta Inmediata (Se notifica a Odoo y al radar en rojo)
Desvío de Itinerario Distancia al trazado oficial > 400 metros Alerta de Desvío (Estado pasa a OFF_ROUTE)
Cruce de Cabecera Ingreso / salida del radio de 150m en origen o destino Evento Odoo (Dispara semáforo de puntualidad de despacho)

EN VIVO Pantallas de Verificación para Pruebas

Durante la conexión, el técnico del proveedor y el equipo de operaciones pueden comprobar en tiempo real la llegada de cada posición abriendo cualquiera de los siguientes tableros:

  • 1
    Radar Satelital GPS en Vivo (WebSockets 0ms)

    Muestra el mapa cartográfico con los buses moviéndose en vivo. Al hacer clic sobre cualquier bus, se muestra su velocidad, odómetro, kilometraje recorrido sobre el trazado oficial y el nombre de la calle actual.
    Acceso directo: http://192.168.1.100:8088/map

  • 2
    Tablero Lineal de Frecuencias e Intervalos (Headway)

    Representa cada ramal como una línea recta de 0 km al final del recorrido. Detecta la distancia en kilómetros y minutos entre cada bus consecutivo y activa alerta de pegonamiento (bunching) si dos buses están a menos de 800m.
    Acceso directo: http://192.168.1.100:8088/headway

  • 3
    Tablero de Cumplimiento Regulatorio e ICF (Decreto 710/2023)

    Auditoría en tiempo real del cumplimiento de cuotas de salidas diarias por servicio (E1, E2, E3), discriminado por franja horaria pico/pos-pico.
    Acceso directo: http://192.168.1.100:8088/compliance

  • 4
    Consola Interactiva Swagger / OpenAPI

    Permite a los ingenieros del proveedor enviar paquetes de prueba con 1 solo clic desde el navegador usando el botón "Try it out".
    Acceso directo: http://192.168.1.100:8088/docs

  • 5
    Sistema ERP Odoo 18 (Despachos y Semáforos)

    En el menú Operaciones de Transporte → Operaciones Diarias → Despachos Diarios, la salida programada del bus cambia automáticamente a estado "En Tránsito" con semáforo 🟢 Verde (a tiempo), 🟡 Amarillo (retraso) o 🔵 Azul (reserva técnica).
    Acceso ERP: http://192.168.1.100:8069

CHECKLIST Protocolo de Prueba en 4 Pasos

Etapa Acción a Realizar por el Proveedor Resultado Esperado en el Servidor
Paso 1 Configurar el endpoint REST o broker MQTT con el token GPS_DEVICE_SECRET_2026. Conexión autorizada (sin errores 401).
Paso 2 Enviar un ping de prueba de 1 móvil asignado (ej: interno 00016 en ramal 020c). Respuesta HTTP 200 con "status": "success" y cálculo de calle.
Paso 3 Abrir el Radar en http://192.168.1.100:8088/map. El colectivo aparece posicionado en el mapa con su velocidad y rumbo.
Paso 4 Verificar en Odoo (Menú Despachos Diarios). El viaje programado pasa a semáforo 🟢 Verde automáticamente.
