Objetivo de la Integración:
Permitir que la flota de colectivos transmita su posición satelital (latitud, longitud, velocidad, rumbo, odómetro y estado de despacho) directamente al microservicio receptor del ERP para:
  • Marcar automáticamente la salida de cabecera y clasificar la puntualidad con el Semáforo GPS (🟢 Verde, 🟡 Amarillo, 🔴 Rojo, 🔵 Azul).
  • Proyectar en vivo las unidades en el Radar Satelital Leaflet con el nombre de la calle y próxima esquina.
  • Calcular el tiempo de espera (ETA) por parada para los pasajeros vía código QR.
  • Auditar el cumplimiento de la cuota diaria exigida por la Resolución GVMT N° 065/2024.

OPCIÓN A Transmisión vía REST API (HTTP POST)

Es el método más sencillo y confiable para realizar pruebas inmediatas de conectividad desde plataformas de monitoreo, módems programables o herramientas de prueba como Postman y cURL.

Parámetro Valor de Configuración Notas
Endpoint URL http://192.168.1.100:8088/api/v1/telemetry También admite el alias /telemetry/gps
Método HTTP POST Envío en el cuerpo de la petición
Header de Autenticación X-Device-Token: GPS_DEVICE_SECRET_2026 Obligatorio. Rechaza peticiones sin token (HTTP 401)
Header de Formato Content-Type: application/json Carga útil en formato JSON UTF-8
Frecuencia de Envío Cada 10 a 30 segundos Intervalo óptimo según estándar de transporte

1. Estructura del Payload JSON

payload_ejemplo.json 
{
  "mean_id": "104",                // N° de Interno del Colectivo en el ERP (Obligatorio)
  "license_plate": "ABC 123",       // Chapa / Matrícula oficial
  "agency_id": "004B",             // Código de Concesionaria / Empresa
  "route_id": "020f",              // Código del Ramal asignado (ej: 020f, E1, etc.)
  "driver_id": "CHOFER-4589",      // Identificador o cédula del chofer (opcional)
  "latitude": -25.314850,          // Latitud WGS84 decimal (Obligatorio)
  "longitude": -57.593210,         // Longitud WGS84 decimal (Obligatorio)
  "velocidad": 35.5,               // Velocidad instantánea en km/h
  "rumbo": 95.0,                   // Ángulo de navegación en grados (0° a 360°)
  "odometer_km": 154230.5,         // Kilometraje acumulado en odómetro
  "precision": 10,                 // Precisión satelital GPS en metros (≤ 50m)
  "altitud": 115.0,                // Altitud sobre el nivel del mar en metros
  "fecha_hora": "2026-10-07T18:30:00Z", // Timestamp UTC formato ISO-8601
  "type": 2                        // Estado: 0 = INICIADO, 2 = OPERANDO, 1 = FINALIZADO
}

OPCIÓN B Transmisión por Broker MQTT (Res. GVMT 065/2024)

Para equipos telemáticos 4G que ya transmiten por protocolo MQTT o al centro de monitoreo del Viceministerio de Transporte (GVMT), el microservicio cuenta con un consumidor Mosquitto integrado de alta disponibilidad.

Parámetro MQTT Valor Oficial Descripción
Broker Host 192.168.1.100 IP o Dominio del servidor central
Puerto MQTT TCP 1883 Puerto estándar Mosquitto para módems 4G / AVL
Puerto WebSockets 9001 Puerto alternativo para navegadores o túneles proxy
Usuario MQTT gps_device Credencial parametrizada en variables de entorno
Contraseña MQTT GPS_DEVICE_SECRET_2026 Clave de acceso para la flota
Tópico Oficial de Publicación transporte/flota/{agency_id}/operacion Ejemplo: transporte/flota/004B/operacion
Calidad de Servicio (QoS) QoS 1 At least once (Garantiza entrega de cada ping)
Formato de Payload Admitido Dual: Protobuf v3 o JSON Plano El broker detecta automáticamente si el paquete es binario o JSON
💡
Compatibilidad Híbrida Automática:
Si su proveedor envía la trama binaria nativa Protocol Buffers v3 compilada con transit.proto (mensaje Operation), el broker la decodifica en < 0.5 ms. Si su módem no soporta Protobuf y envía JSON por MQTT, el broker lo reconoce instantáneamente sin requerir ningún cambio.

Esquema Protobuf v3 Oficial (`transit.proto`):

transit.proto 
// Protocol Buffers v3 - Res. GVMT N° 065/2024
syntax = "proto3";
package transit;

enum OperationType {
  INICIADO = 0;   // Salida de terminal
  FINALIZADO = 1; // Fin de recorrido
  OPERANDO = 2;   // Circulando en ruta
}

message Operation {
  string agency_id = 1;     // Código empresa (ej: "004B")
  string mean_id = 2;       // N° de bus (ej: "104")
  string route_id = 3;      // Ramal (ej: "020f")
  string driver_id = 4;     // Chofer
  OperationType type = 5;   // Estado del viaje
  int32 accuracy = 6;       // Precisión GPS (metros)
  string datetime_utc = 7;  // Timestamp ISO-8601
  double latitude = 8;      // Latitud WGS84
  double longitude = 9;     // Longitud WGS84
  double altitude = 10;     // Altitud
  double bearing = 11;      // Rumbo
  double speed = 12;        // Velocidad en km/h
}

EN VIVO Pantallas de Verificación para la Prueba

Durante la prueba de envío, el equipo técnico y los jefes de tráfico pueden verificar la recepción inmediata a través de cuatro pantallas operativas:

  • Radar Satelital en Vivo (Leaflet / WebSockets)

    Muestra el mapa georreferenciado con los colectivos moviéndose en tiempo real. Al hacer clic sobre cualquier bus, se muestra su velocidad, odómetro, kilometraje de itinerario y su ubicación en lenguaje natural.
    Acceso web: http://192.168.1.100:8088/map

  • Tablero Lineal de Frecuencias y Detector de Pegonamiento (Headway)

    Representa cada ramal como una línea recta horizontal de 0.0 km al final del recorrido. Calcula la separación exacta en kilómetros y minutos entre cada coche y genera una alerta roja si dos colectivos están a menos de 800 metros (< 2 min).
    Acceso web: http://192.168.1.100:8088/headway

  • Consola Interactiva Swagger / OpenAPI (Pruebas con 1 Clic)

    Interfaz web para que los técnicos prueben el envío de paquetes directamente desde su navegador con el botón "Try it out".
    Acceso web: http://192.168.1.100:8088/docs

  • Sistema ERP Odoo 18 (Despachos Diarios y Semáforos)

    En el módulo de Operaciones Diarias → Despachos Diarios, el sistema detecta el cruce de geocerca de salida y activa el semáforo automático:
    • 🟢 Verde: Salida a tiempo dentro de la tolerancia programada.
    • 🟡 Amarillo: Salida con retraso fuera de margen.
    • 🔴 Rojo: Despacho cancelado o faltante.
    • 🔵 Azul: Despacho cubierto por bus de reserva técnica.
    Acceso ERP: http://192.168.1.100:8069

DICCIONARIO Campos del Protocolo y Reglas de Negocio

Catálogo completo de campos aceptados por el microservicio telemático, sus tipos, rangos válidos y reglas de descarte automático según la Resolución GVMT N° 065/2024:

Campo Tipo Requerido Descripción y Regla de Validación
mean_id String Sí Número de interno o identificador único del colectivo (ej: "104"). Si no viene, se busca en bus_id.
latitude Float Sí Coordenada latitud en WGS84 decimal. Se descartan coordenadas con valor 0.0 o fuera del rango [-90, 90].
longitude Float Sí Coordenada longitud en WGS84 decimal. Se descartan coordenadas con valor 0.0 o fuera del rango [-180, 180].
agency_id String No Código de la empresa concesionaria (ej: "004B"). Por defecto toma la empresa configurada.
route_id String No Código del ramal o servicio (ej: "020f", "E1"). Permite calcular el avance sobre el trazado PostGIS.
velocidad / speed_kmh Float No Velocidad instantánea en km/h. Si supera los 70.0 km/h, genera alerta automática de exceso de velocidad.
rumbo / heading_deg Float No Orientación del vehículo en grados (0.0° a 360.0°). Usado para proyectar la dirección en el radar.
odometer_km Float No Kilometraje acumulado. Al completar el viaje, se guarda automáticamente en la ficha del bus en Odoo.
precision Integer No Margen de error GPS en metros. Pings con precision > 50m se marcan con bandera de baja precisión.
type Integer No Estado operativo: 0 = INICIADO (Salida), 2 = OPERANDO (En ruta), 1 = FINALIZADO (Llegada).
fecha_hora / timestamp ISO-8601 No Fecha y hora UTC del satélite (ej: "2026-10-07T18:30:00Z"). Si se omite, se usa la hora del servidor.
⚠️
Criterio de Descarte Oficial:
Siguiendo la Sección 5.1 de la Resolución GVMT N° 065/2024, el servidor descartará automáticamente pings con coordenadas (0.0, 0.0) o lecturas que no correspondan a la República del Paraguay para preservar la integridad de las estadísticas de puntualidad y cumplimiento.

CHECKLIST Pasos para Realizar la Primera Prueba

Paso Acción a Realizar Resultado Esperado
Paso 1 Configurar el endpoint REST o broker MQTT en el dispositivo o plataforma de pruebas con el token GPS_DEVICE_SECRET_2026. Conexión establecida sin errores de autenticación.
Paso 2 Enviar un paquete de prueba con 1 colectivo (ej: interno 104 con coordenadas reales de la ruta). Respuesta HTTP 200 con JSON indicando "status": "success".

Paso 4 Verificar en Odoo ERP (Menú Despachos Diarios). El despacho cambia automáticamente a "En Tránsito" y el semáforo marca 🟢 Verde.
