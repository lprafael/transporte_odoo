s horarias)
event_dt = fields.Datetime.to_datetime(event_time_str.replace( 'Z' ,  '+00:00' ))
# 6. Procesar según el evento
try :
if  event_type ==  'departure' :
dispatch.write({
'actual_departure' : event_dt,
'initial_odometer' : odometer  or  dispatch.initial_odometer,
'state' :  'in_transit' ,
})
# Forzar recálculo de puntualidad
dispatch._compute_performance()
elif  event_type ==  'checkpoint' :
env[ 'transit.dispatch.checkpoint' ].sudo().create({
'dispatch_id' : dispatch. id ,
'name' : checkpoint_name,
'actual_time' : event_dt,
})
elif  event_type ==  'arrival' :
dispatch.write({
'actual_arrival' : event_dt,
'final_odometer' : odometer  or  dispatch.final_odometer,
'state' :  'completed' ,
})
dispatch.action_complete()
else :
return  Response(
json.dumps({ 'error' :  f'Tipo de evento no reconocido:  {event_type} ' ,  'code' :  400 }),
status= 400 ,
content_type= 'application/json'
)
except  Exception  as  e:
_logger.exception( "Error procesando evento GPS en Odoo" )
return  Response(
json.dumps({ 'error' :  str (e),  'code' :  500 }),
status= 500 ,
content_type= 'application/json'
)
return  Response(
json.dumps({
'status' :  'success' ,
'dispatch_id' : dispatch. id ,
'dispatch_name' : dispatch.name,
'state' : dispatch.state,
'compliance_status' : dispatch.compliance_status,
'delay_minutes' : dispatch.departure_delay_minutes
}),
status= 200 ,
content_type= 'application/json'
)
4. Buenas Prácticas y Resiliencia
Idempotencia:  Si el GPS pierde cobertura e intenta reenviar el evento 3 veces, el endpoint debe validar que si  actual_departure  ya tiene un valor cargado, no sobreescriba la hora original ni duplique checkpoints.
Buffer de Desconexión:  Si los eventos llegan en lote ( batch ) porque el bus estuvo en zona sin señal, el servicio receptor debe ordenar los registros por el campo  timestamp  del dispositivo antes de procesar el estado en Odoo.
Manejo de Zonas Horarias:  Odoo almacena internamente todos los campos  Datetime  en  UTC . Asegurate de que el ingestor siempre serialice en formato ISO 8601 con sufijo  Z  ( 2026-09-21T10:15:00Z ).

Cómo funciona un broker de mensajería? para recibir datos GPS de la empresa operadora de transporte?
Un  broker de mensajería  actúa como una "estación central de correos" o intermediario asíncrono entre los dispositivos emisores (los buses transmitiendo datos telemáticos) y los sistemas receptores (tu base de datos, motor de geocercas, visores en tiempo real o el ERP).
1. El problema que resuelve: Por qué no conectar los buses directo a Odoo / Base de Datos
Si tienes una flota de 100 buses y cada uno envía una trama GPS cada 5 o 10 segundos:
Estás recibiendo  10 a 20 peticiones por segundo de forma continua .
Si la base de datos o el ERP tiene un pico de carga, una transacción bloqueada o entra en mantenimiento por 30 segundos,  las conexiones de los buses rebotan, colapsan el servidor HTTP o se pierden las coordenadas .
Si además necesitas que esa misma coordenada la lea:
El mapa en vivo para los usuarios.
El motor de geocercas que calcula retrasos e itinerarios.
El almacenamiento histórico.
Hacer que el bus envíe 3 peticiones HTTP separadas consume datos móviles del módem del bus y vuelve al sistema frágil.
2. El modelo Publicador / Suscriptor ( Pub/Sub )
Los brokers de mensajería modernos (como  EMQX / Mosquitto  para MQTT, o  RabbitMQ / Redis Streams / Apache Kafka ) utilizan el patrón  Publicador/Suscriptor :
[Bus #102] ──(Publish)──► Topic: "flota/linea101/bus102/telemetria"
│
▼
┌─────────────────────────┐
│  BROKER DE MENSAJERÍA   │
│   (Memoria / Cola FIFO) │
└───────────┬─────────────┘
│
┌─────────────────────┼─────────────────────┐
▼                     ▼                     ▼
[Servicio Ingestor]    [Motor de Geocercas]   [WebSocket Web]
(Guarda en DB)        (Calcula demoras/Odoo)  (Mapa en vivo)
Desacoplamiento total:  El bus no sabe quién lee el dato ni le importa; solo publica su paquete al broker y queda libre.
Buffer / Colas de retención (Backpressure):  Si tu servidor de Odoo o la base de datos se cae por 5 minutos, el broker acumula los mensajes en memoria/disco en una cola ordenada. Cuando el servidor vuelve a estar en línea, procesa todo el historial acumulado sin perder un solo metro de recorrido.
Distribución 1 a N ( Fan-out ):  Un único mensaje entrante puede ser consumido en paralelo por distintos microservicios a la velocidad que cada uno necesite.
3. Protocolos más comunes en transporte: MQTT vs HTTP
Para dispositivos embebidos en buses (computadoras a bordo, validadores o rastreadores AVL), el protocolo rey es  MQTT  (Message Queuing Telemetry Transport):
Característica    HTTP tradicional (REST)    MQTT (vía Broker)
Conexión     Abre y cierra conexión TCP por cada punto GPS    Mantiene  una única conexión TCP abierta  y persistente
Cabecera (Overhead)     ~500 a 1000 bytes solo en cabeceras HTTP     2 bytes  de cabecera fija
Consumo de datos móviles     Alto (costoso en chips 4G/IoT)    Mínimo (ideal para planes de datos limitados)
Calidad de Servicio (QoS)     Requiere reintentos manuales    Soporta  QoS 0  (al menos una vez),  QoS 1 ,  QoS 2  nativo
Latencia     Variable (apretón de manos recurrente)    Inmediata (< 50 ms)
4. Flujo operativo paso a paso
El módem del bus envía el paquete:
El dispositivo a bordo publica un JSON comprimido en el  topic :
empresa/flota/bus-04/posicion
JSON
{
"bus_id" :  "04" ,
"timestamp" :  1727213442 ,
"lat" :  -25.3214 ,
"lon" :  -57.5621 ,
"speed" :  42.5 ,
"odometer" :  189420.3
}
El Broker recibe y enruta:
El broker (ej. EMQX o Mosquitto) autentica la unidad por certificado o usuario/contraseña, y pone el mensaje a disposición de los clientes suscritos al patrón  empresa/flota/+/posicion .
Los Consumidores procesan:
Consumidor A (Geofencing / Reglas):  Un microservicio ligero (en Python o Go) recibe el mensaje, valida si el punto cayó dentro del radio de 30 metros de la parada o cabecera, y si detecta llegada o salida, hace el llamado al endpoint de Odoo que definimos anteriormente ( POST /api/v1/transit/events ).
Consumidor B (Histórico / Big Data):  Escribe el punto directamente en una base temporal o serie de tiempo (TimescaleDB / PostGIS).
Consumidor C (Monitoreo en vivo):  Reenvía por WebSocket al navegador de los despachadores para pintar el colectivo moviéndose en el mapa.
5. ¿Qué broker elegir según el volumen?
Mosquitto / EMQX:  Si tus buses o validadores transmiten directamente vía  MQTT . EMQX es especialmente potente porque incluye un motor de reglas interno que puede disparar webhooks HTTP directamente sin escribir código intermedio.
RabbitMQ:  Excelente si recibes datos por HTTP o sockets en un ingestor y necesitas colas de trabajo garantizadas con lógica compleja de reintentos y enrutamiento hacia Odoo o bases de datos.
Redis Streams:  Muy rápido, liviano y fácil de levantar en tu mismo  docker-compose.yml  para proyectos medianos (decenas a cientos de buses).

Cual es el protocolo recomendado? MQTT o HTTP?
Para telemetría vehicular en transporte público,  MQTT es el estándar indiscutido y la recomendación técnica por excelencia , con una salvedad muy clara:  depende de qué dispositivo esté emitiendo el dato .
Comparativa directa en campo
Criterio    MQTT (Recomendado para telemetría)    HTTP / REST
Overhead de red     Cabecera fija de  2 bytes .    Cabecera de  500 a 1.000+ bytes  por petición (headers, user-agent, cookies, etc.).
Consumo de datos móviles     Mínimo. En un escenario de 100 buses enviando datos cada 5 s, el ahorro de datos en el chip SIM suele rondar el  60% al 80% .    Alto. Transmite más metadatos de cabecera que información útil de lat/lon.
Modelo de conexión      1 sola conexión TCP persistente  con  keep-alive  (paquetes mínimos tipo ping).    Abre y cierra conexión TCP (Handshake TLS/TCP continuo).
Comportamiento ante zonas sin señal     Reconexión automática nativa; maneja desconexiones intermitentes sin colapsar el socket.    Múltiples reintentos que agotan timeouts y saturan la cola del módem 3G/4G.
Latencia     En tiempo real (< 50–100 ms).    Moderada (150–500+ ms por el ciclo de petición/respuesta).
Bidireccionalidad     Inmediata. El servidor puede enviar un comando al bus (ej: cortar combustible, resetear validador) al instante.    Compleja. El bus tiene que hacer  polling  o requerir IP pública fija (muy costoso en telefonía celular).
La excepción en la práctica: ¿Quién transmite el dato?
En el transporte público real existen dos escenarios muy distintos:
Escenario 1: El bus transmite directamente a tu servidor (Gana MQTT)
Si controlas el firmware del validador de billetaje, tienes una computadora de a bordo (Raspberry Pi/Linux embebido) o utilizas un rastreador AVL programable (como Teltonika o Suntech que soportan MQTT nativo):
Elección obligatoria:   MQTT .
Reduces el costo mensual de los planes de datos móviles de la flota y aseguras fluidez en mapas en tiempo real.
Escenario 2: La empresa operadora te entrega los datos vía API de un tercero (Se usa HTTP)
Si los buses ya transmiten a la plataforma del proveedor del GPS o del sistema de billetaje (ej. Geotab, Traccar o el proveedor del validador) y esa empresa te provee a ti la información:
En este caso, la empresa casi siempre entrega un  Webhook HTTP  o una  API REST (JSON) .
Elección:  Consumir ese  HTTP/Webhook , pero recibirlo en un microservicio ligero (como FastAPI o Node.js) que actúe de adaptador,  nunca directamente en Odoo .

Si, muestrame la estrategia de particionado o retención de datos en PostgreSQL para que no crezca indefinidamente
Para evitar que la base de datos se degrade o consuma todo el disco con los millones de puntos GPS, la estrategia estándar en PostgreSQL combina dos técnicas:
Particionado declarativo por rango de fechas (mensual o semanal):  Permite aislar los datos en tablas hijas.
Purgado instantáneo con  DROP TABLE :  Eliminar un mes viejo borrando la partición completa toma  milisegundos  y no genera  bloat  (espacio muerto) ni bloqueos de tabla, a diferencia de un  DELETE FROM ... WHERE fecha < ... , que satura el log de transacciones (WAL) y degrada el rendimiento.
1. Creación de la tabla particionada en PostgreSQL
Definimos la tabla principal indicando que se particionará por la columna  recorded_at :
SQL
-- Habilitar extensión espacial si aún no está activa
CREATE  EXTENSION IF  NOT   EXISTS  postgis;
-- Tabla principal particionada por RANGO de tiempo
CREATE   TABLE  telemetry_ping (
id BIGSERIAL,
bus_internal_code  VARCHAR ( 20 )  NOT   NULL ,
recorded_at TIMESTAMPTZ  NOT   NULL ,
geom GEOMETRY(Point,  4326 ),
speed_kmh  NUMERIC ( 5 ,  2 ),
heading_degrees  SMALLINT ,
odometer_km  NUMERIC ( 10 ,  2 ),
created_at TIMESTAMPTZ  DEFAULT   CURRENT_TIMESTAMP ,
-- La clave primaria debe incluir obligatoriamente la columna de partición
PRIMARY  KEY (id, recorded_at)
)  PARTITION   BY   RANGE  (recorded_at);
-- Índices en la tabla base (PostgreSQL los propaga automáticamente a cada partición)
CREATE  INDEX idx_telemetry_bus_time
ON  telemetry_ping (bus_internal_code, recorded_at  DESC );
CREATE  INDEX idx_telemetry_geom
ON  telemetry_ping  USING  GIST (geom);

3. Automatización de creación de particiones y política de retención
Para no crear tablas a mano cada mes ni preocuparte por el borrado manual, creamos una función en PL/pgSQL que:
Crea la partición del mes actual y del mes siguiente (para asegurar que siempre haya dónde escribir).
Elimina (o desacopla) las particiones que superen la política de retención (ej.  más de 90 días / 3 meses de antigüedad ).
SQL
CREATE   OR  REPLACE  FUNCTION  maintain_telemetry_partitions(retention_months  INTEGER   DEFAULT   3 )
RETURNS  VOID  AS  $$
DECLARE
v_date  DATE ;
v_next_month  DATE ;
v_partition_name TEXT;
v_start_time TIMESTAMPTZ;
v_end_time TIMESTAMPTZ;
v_old_partition TEXT;
BEGIN
-- 1. Crear particiones: mes actual y mes siguiente
FOR  i  IN   0.  .1  LOOP
v_date : =  date_trunc( 'month' ,  CURRENT_DATE   +  (i  ||   ' month' ):: INTERVAL );
v_next_month : =  v_date  +   INTERVAL   '1 month' ;
v_partition_name : =   'telemetry_ping_'   ||  to_char(v_date,  'YYYY_MM' );
v_start_time : =  v_date::TIMESTAMPTZ;
v_end_time : =  v_next_month::TIMESTAMPTZ;
-- Verificar si ya existe antes de crear
IF  NOT   EXISTS  (
SELECT   1   FROM  pg_class c
JOIN  pg_namespace n  ON  n.oid  =  c.relnamespace
WHERE  c.relname  =  v_partition_name
)  THEN
EXECUTE  format(
'CREATE TABLE %I PARTITION OF telemetry_ping FOR VALUES FROM (%L) TO (%L);' ,
v_partition_name, v_start_time, v_end_time
);
RAISE NOTICE  'Partición creada: %' , v_partition_name;
END  IF;
END  LOOP;
-- 2. Eliminar particiones más viejas que el período de retención
FOR  v_old_partition  IN
SELECT  c.relname
FROM  pg_class c
JOIN  pg_inherits i  ON  i.inhrelid  =  c.oid
JOIN  pg_class parent  ON  f_parent.oid  =  i.inhparent
WHERE  parent.relname  =   'telemetry_ping'
AND  c.relname  <  ( 'telemetry_ping_'   ||  to_char( CURRENT_DATE   -  (retention_months  ||   ' month' ):: INTERVAL ,  'YYYY_MM' ))
LOOP
-- Desasociar y destruir la tabla vieja en microsegundos
EXECUTE  format( 'DROP TABLE IF EXISTS %I;' , v_old_partition);
RAISE NOTICE  'Partición eliminada por política de retención: %' , v_old_partition;
END  LOOP;
END ;
$$  LANGUAGE  plpgsql;

Para respaldar un entorno completo de Odoo y PostgreSQL en un VPS de producción,  no basta con respaldar la base de datos : también es obligatorio respaldar el   filestore   de Odoo (donde se almacenan los adjuntos, fotos de unidades, documentos de seguro e imágenes de la flota) y tus módulos personalizados.
La estrategia más sólida y estándar en entornos Linux con Docker es utilizar un script en Bash automatizado con  cron  que genere un archivo comprimido  .tar.gz  con fecha, aplique retención local y lo sincronice con un almacenamiento externo (como Google Drive, AWS S3 o un servidor remoto) usando  Rclone .
1. Estructura de respaldos en el VPS
Creá una carpeta dedicada para los backups fuera del árbol del proyecto:
Bash
sudo mkdir -p /opt/backups/flota
sudo chown -R  $USER : $USER  /opt/backups
2. El script de respaldo automatizado ( backup_flota.sh )
Creá el script en  /opt/backups/backup_flota.sh :
Bash
nano /opt/backups/backup_flota.sh
Pegá el siguiente contenido:
Bash
#!/usr/bin/env bash
# ==============================================================================
# Script de Respaldo Integral: PostgreSQL + Odoo Filestore + Addons
# ==============================================================================
set  -eo pipefail
# 1. Variables de configuración
TIMESTAMP=$(date + "%Y%m%d_%H%M%S" )
BACKUP_DIR= "/opt/backups/flota"
TEMP_DIR= " ${BACKUP_DIR} /temp_ ${TIMESTAMP} "
RETENTION_DAYS=7    # Días que se conservan backups locales en el VPS
# Nombres de contenedores y base de datos (según tu docker-compose)
DB_CONTAINER= "transporte_odoo-db-1"
DB_USER= "odoo"
DB_NAME= "flota_db"
# Rutas del proyecto y volúmenes
PROJECT_DIR= "/opt/transporte_odoo"
ODOO_FILESTORE_VOLUME= "transporte_odoo_odoo-web-data"   # Nombre del volumen docker
FINAL_ARCHIVE= " ${BACKUP_DIR} /backup_completo_ ${DB_NAME} _ ${TIMESTAMP} .tar.gz"
echo   "[ $(date) ] Iniciando proceso de respaldo..."
# Crear directorios temporales
mkdir -p  " ${TEMP_DIR} /db"
mkdir -p  " ${TEMP_DIR} /filestore"
mkdir -p  " ${TEMP_DIR} /config_custom"
# 2. Dump de la Base de Datos PostgreSQL (en formato binario comprimido)
echo   "[ $(date) ] Extrayendo base de datos PostgreSQL ( ${DB_NAME} )..."
docker  exec  -t  " ${DB_CONTAINER} "  pg_dump -U  " ${DB_USER} "  -d  " ${DB_NAME} "  -F c -b -v -f  "/tmp/db_dump_ ${TIMESTAMP} .dump"
docker cp  " ${DB_CONTAINER} :/tmp/db_dump_ ${TIMESTAMP} .dump"   " ${TEMP_DIR} /db/ ${DB_NAME} .dump"
docker  exec  -t  " ${DB_CONTAINER} "  rm  "/tmp/db_dump_ ${TIMESTAMP} .dump"
# 3. Copia del Filestore de Odoo (imágenes, adjuntos, reportes PDF)
echo   "[ $(date) ] Copiando filestore de Odoo..."
# Se copia directamente del volumen local de Docker
docker run --rm -v  " ${ODOO_FILESTORE_VOLUME} :/data:ro"  -v  " ${TEMP_DIR} /filestore:/backup"  alpine cp -a /data/filestore /backup/
# 4. Copia de configuraciones y módulos custom
echo   "[ $(date) ] Respaldando módulos personalizados y configuración..."
cp -r  " ${PROJECT_DIR} /custom_addons"   " ${TEMP_DIR} /config_custom/"
cp  " ${PROJECT_DIR} /config/odoo.conf"   " ${TEMP_DIR} /config_custom/"
cp  " ${PROJECT_DIR} /docker-compose.yml"   " ${TEMP_DIR} /config_custom/"
# 5. Comprimir todo en un único archivo .tar.gz
echo   "[ $(date) ] Empaquetando y comprimiendo archivo final..."
tar -czf  " ${FINAL_ARCHIVE} "  -C  " ${TEMP_DIR} "  .
# Limpieza temporal
rm -rf  " ${TEMP_DIR} "
echo   "[ $(date) ] Archivo generado con éxito:  ${FINAL_ARCHIVE}  ( $(du -h  " ${FINAL_ARCHIVE} "  | awk '{print $1}') )"
# 6. Purgar backups locales antiguos (mantener últimos 7 días)
echo   "[ $(date) ] Eliminando backups locales con más de  ${RETENTION_DAYS}  días..."
find  " ${BACKUP_DIR} "  -name  "backup_completo_*.tar.gz"  -mtime + " ${RETENTION_DAYS} "  - exec  rm -f {} \;
# 7. Sincronizar a la nube con Rclone (Opcional pero crítico)
# Si configurás un remote llamado 'remote_flota' (Google Drive, S3, etc.):
if   command  -v rclone &> /dev/null;  then
echo   "[ $(date) ] Sincronizando respaldo con almacenamiento en la nube (Rclone)..."
rclone copy  " ${FINAL_ARCHIVE} "  remote_flota:backups_flota_vps/
fi
echo   "[ $(date) ] Proceso de respaldo finalizado exitosamente."
Asignale permisos de ejecución:
Bash

## 1. Esquema Protocol Buffer (proto3)
El proveedor transmitirá el payload en formato binario serializado respetando exactamente el siguiente contrato protobuf:
```protobuf
syntax = "proto3";
package transit.telemetry;
import "google/protobuf/timestamp.proto";
message Operation {
enum OperationType {
INICIADO = 0;
FINALIZADO = 1;
OPERANDO = 2;
SUSPENDIDO = 3;
}
// Campos Requeridos
int32 identidad = 1;                    // ID de la entidad emisora
string agency_id = 2;                   // ID de la Empresa Operadora de Transporte
string mean_id = 3;                     // Identificador de la unidad/bus (placa o interno)
string route_id = 4;                    // Identificador de la ruta o ramal
string driver_id = 5;                   // ID o documento del conductor
OperationType type = 6;                 // Estado operativo del servicio
int32 accuracy = 7;                     // Precisión del GPS en metros
double latitude = 8;                    // Latitud WGS 84
double longitude = 9;                   // Longitud WGS 84
google.protobuf.Timestamp datetime = 13;// Fecha/Hora UTC de emisión del mensaje
// Campos Opcionales
double altitude = 10;                   // Altitud en metros sobre el nivel del mar
double bearing = 11;                    // Rumbo/Dirección en grados (0° a 360°)
double speed = 12;                      // Velocidad del móvil en km/h
}
2. Requerimientos de Red y Transporte
Protocolo de capa de aplicación:  MQTT v3.1.1 o v5.0.
Frecuencia de muestreo:  10 segundos por bus.
Topología de topics en el Broker:   transporte/flota/{agency_id}/operacion  (donde se publica el binario).
3. Arquitectura del Ingestor en Antigravity
Debes implementar un servicio consumidor desacoplado en Python (usando  aiomqtt  o  paho-mqtt  +  asyncpg ):
Decodificación Protobuf:
Compilar el archivo  .proto  con  protoc .
Deserializar  Operation.FromString(payload_bytes) .
Convertir  datetime  ( google.protobuf.Timestamp ) a objetos  datetime.datetime  con zona horaria UTC explícita.
Capa de Almacenamiento (PostgreSQL + PostGIS):
Insertar de forma masiva o asíncrona en la tabla particionada  telemetry_ping :
bus_internal_code  =  mean_id
recorded_at  =  datetime
geom  =  ST_SetSRID(ST_MakePoint(longitude, latitude), 4326)
speed_kmh  =  speed
heading_degrees  =  bearing
Capa de Detección de Eventos (Hacia Odoo ERP):
Evaluar si el bus cambia de estado ( type == INICIADO  o  type == FINALIZADO ) o si entra/sale de las geocercas de cabeceras/paradas.
Si se detecta un hito de despacho, invocar el webhook HTTP de Odoo ( /api/v1/transit/events ) enviando  license_plate = mean_id ,  event_type  ('departure'/'arrival') y  timestamp .
IMPORTANTE:  No enviar los pings continuos de  OPERANDO  a Odoo; solo los eventos discretos consolidados.
