Cómo funciona un broker de mensajería? para recibir datos GPS de la empresa operadora de transporte? Un broker de mensajería actúa como una "estación central de correos" o intermediario asíncrono entre los dispositivos emisores (los buses transmitiendo datos telemáticos) y los sistemas receptores (tu base de datos, motor de geocercas, visores en tiempo real o el ERP). 1. El problema que resuelve: Por qué no conectar los buses directo a Odoo / Base de Datos Si tienes una flota de 100 buses y cada uno envía una trama GPS cada 5 o 10 segundos: Estás recibiendo 10 a 20 peticiones por segundo de forma continua . Si la base de datos o el ERP tiene un pico de carga, una transacción bloqueada o entra en mantenimiento por 30 segundos, las conexiones de los buses rebotan, colapsan el servidor HTTP o se pierden las coordenadas . Si además necesitas que esa misma coordenada la lea: El mapa en vivo para los usuarios. El motor de geocercas que calcula retrasos e itinerarios. El almacenamiento histórico. Hacer que el bus envíe 3 peticiones HTTP separadas consume datos móviles del módem del bus y vuelve al sistema frágil. 2. El modelo Publicador / Suscriptor ( Pub/Sub ) Los brokers de mensajería modernos (como EMQX / Mosquitto para MQTT, o RabbitMQ / Redis Streams / Apache Kafka ) utilizan el patrón Publicador/Suscriptor : [Bus #102] ──(Publish)──► Topic: "flota/linea101/bus102/telemetria" │ ▼ ┌─────────────────────────┐ │ BROKER DE MENSAJERÍA │ │ (Memoria / Cola FIFO) │ └───────────┬─────────────┘ │ ┌─────────────────────┼─────────────────────┐ ▼ ▼ ▼ [Servicio Ingestor] [Motor de Geocercas] [WebSocket Web] (Guarda en DB) (Calcula demoras/Odoo) (Mapa en vivo) Desacoplamiento total: El bus no sabe quién lee el dato ni le importa; solo publica su paquete al broker y queda libre. Buffer / Colas de retención (Backpressure): Si tu servidor de Odoo o la base de datos se cae por 5 minutos, el broker acumula los mensajes en memoria/disco en una cola ordenada. Cuando el servidor vuelve a estar en línea, procesa todo el historial acumulado sin perder un solo metro de recorrido. Distribución 1 a N ( Fan-out ): Un único mensaje entrante puede ser consumido en paralelo por distintos microservicios a la velocidad que cada uno necesite. 3. Protocolos más comunes en transporte: MQTT vs HTTP Para dispositivos embebidos en buses (computadoras a bordo, validadores o rastreadores AVL), el protocolo rey es MQTT (Message Queuing Telemetry Transport): Característica HTTP tradicional (REST) MQTT (vía Broker) Conexión Abre y cierra conexión TCP por cada punto GPS Mantiene una única conexión TCP abierta y persistente Cabecera (Overhead) ~500 a 1000 bytes solo en cabeceras HTTP 2 bytes de cabecera fija Consumo de datos móviles Alto (costoso en chips 4G/IoT) Mínimo (ideal para planes de datos limitados) Calidad de Servicio (QoS) Requiere reintentos manuales Soporta QoS 0 (al menos una vez), QoS 1 , QoS 2 nativo Latencia Variable (apretón de manos recurrente) Inmediata (&lt; 50 ms) 4. Flujo operativo paso a paso El módem del bus envía el paquete: El dispositivo a bordo publica un JSON comprimido en el topic : empresa/flota/bus-04/posicion JSON { "bus_id" : "04" , "timestamp" : 1727213442 , "lat" : -25.3214 , "lon" : -57.5621 , "speed" : 42.5 , "odometer" : 189420.3 } El Broker recibe y enruta: El broker (ej. Automatización de creación de particiones y política de retención Para no crear tablas a mano cada mes ni preocuparte por el borrado manual, creamos una función en PL/pgSQL que: Crea la partición del mes actual y del mes siguiente (para asegurar que siempre haya dónde escribir). Elimina (o desacopla) las particiones que superen la política de retención (ej. más de 90 días / 3 meses de antigüedad ). SQL CREATE OR REPLACE FUNCTION maintain_telemetry_partitions(retention_months INTEGER DEFAULT 3 ) RETURNS VOID AS $$ DECLARE v_date DATE ; v_next_month DATE ; v_partition_name TEXT; v_start_time TIMESTAMPTZ; v_end_time TIMESTAMPTZ; v_old_partition TEXT; BEGIN -- 1. Crear particiones: mes actual y mes siguiente FOR i IN 0. .1 LOOP v_date : = date_trunc( 'month' , CURRENT_DATE + (i || ' month' ):: INTERVAL ); v_next_month : = v_date + INTERVAL '1 month' ; v_partition_name : = 'telemetry_ping_' || to_char(v_date, 'YYYY_MM' ); v_start_time : = v_date::TIMESTAMPTZ; v_end_time : = v_next_month::TIMESTAMPTZ; -- Verificar si ya existe antes de crear IF NOT EXISTS ( SELECT 1 FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace WHERE c.relname = v_partition_name ) THEN EXECUTE format( 'CREATE TABLE %I PARTITION OF telemetry_ping FOR VALUES FROM (%L) TO (%L);' , v_partition_name, v_start_time, v_end_time ); RAISE NOTICE 'Partición creada: %' , v_partition_name; END IF; END LOOP; -- 2. Eliminar particiones más viejas que el período de retención FOR v_old_partition IN SELECT c.relname FROM pg_class c JOIN pg_inherits i ON i.inhrelid = c.oid JOIN pg_class parent ON f_parent.oid = i.inhparent WHERE parent.relname = 'telemetry_ping' AND c.relname &lt; ( 'telemetry_ping_' || to_char( CURRENT_DATE - (retention_months || ' month' ):: INTERVAL , 'YYYY_MM' )) LOOP -- Desasociar y destruir la tabla vieja en microsegundos EXECUTE format( 'DROP TABLE IF EXISTS %I;' , v_old_partition); RAISE NOTICE 'Partición eliminada por política de retención: %' , v_old_partition; END LOOP; END ; $$ LANGUAGE plpgsql; 4.
