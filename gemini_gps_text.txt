Para integrar un sistema de telemetría o GPS externo (como Traccar, Geotab o un servicio propio) con Odoo sin degradar el rendimiento del ERP, la clave está en el
desacoplamiento arquitectónico
.
El GPS no debe enviar millones de coordenadas crudas a Odoo; debe procesarlas en un servicio intermedio que detecte geocercas/eventos y notifique a Odoo únicamente cuando ocurra un hito operativo.
1. Diagrama de flujo de datos
[Buses / AVL] 
     │ (Telemetría UDP/MQTT cada 5s)
     ▼
[Servidor de Telemetría / Ingestor (Traccar / FastAPI)]
     │
     ├─ Detección de Geocercas (Entrada/Salida Cabeceras y Checkpoints)
     ├─ Matching con Servicio Activo
     │
     ▼ (Webhook HTTP REST con Bearer Token)
[Odoo ERP: /api/v1/transit/events]
     │
     ├─ Validación de Token de Sistema
     ├─ Búsqueda del `transit.dispatch` activo
     └─ Registro de cumplimiento y actualización de odómetro

4. Buenas Prácticas y Resiliencia
Idempotencia:
Si el GPS pierde cobertura e intenta reenviar el evento 3 veces, el endpoint debe validar que si
actual_departure
ya tiene un valor cargado, no sobreescriba la hora original ni duplique checkpoints.
Buffer de Desconexión:
Si los eventos llegan en lote (
batch
) porque el bus estuvo en zona sin señal, el servicio receptor debe ordenar los registros por el campo
timestamp
del dispositivo antes de procesar el estado en Odoo.
Manejo de Zonas Horarias:
Odoo almacena internamente todos los campos
Datetime
en
UTC
. Asegurate de que el ingestor siempre serialice en formato ISO 8601 con sufijo
Z
(
2026-09-21T10:15:00Z
).

Cómo funciona un broker de mensajería? para recibir datos GPS de la empresa operadora de transporte?
Cómo funciona un broker de mensajería? para recibir datos GPS de la empresa operadora de transporte?
Un
broker de mensajería
actúa como una "estación central de correos" o intermediario asíncrono entre los dispositivos emisores (los buses transmitiendo datos telemáticos) y los sistemas receptores (tu base de datos, motor de geocercas, visores en tiempo real o el ERP).
1. El problema que resuelve: Por qué no conectar los buses directo a Odoo / Base de Datos
Si tienes una flota de 100 buses y cada uno envía una trama GPS cada 5 o 10 segundos:
Estás recibiendo
10 a 20 peticiones por segundo de forma continua
.
Si la base de datos o el ERP tiene un pico de carga, una transacción bloqueada o entra en mantenimiento por 30 segundos,
las conexiones de los buses rebotan, colapsan el servidor HTTP o se pierden las coordenadas
.
Si además necesitas que esa misma coordenada la lea:
El mapa en vivo para los usuarios.
El motor de geocercas que calcula retrasos e itinerarios.
El almacenamiento histórico.
Hacer que el bus envíe 3 peticiones HTTP separadas consume datos móviles del módem del bus y vuelve al sistema frágil.
2. El modelo Publicador / Suscriptor (
Pub/Sub
)
Los brokers de mensajería modernos (como
EMQX / Mosquitto
para MQTT, o
RabbitMQ / Redis Streams / Apache Kafka
) utilizan el patrón
Publicador/Suscriptor
:
[Bus #102] ──(Publish)──► Topic: "flota/linea101/bus102/telemetria"
                                │
                                ▼
                    ┌─────────────────────────┐
                    │  BROKER DE MENSAJERÍA   │
                    │   (Memoria / Cola FIFO) │
                    └───────────┬─────────────┘
                                │
          ┌─────────────────────┼─────────────────────┐
          ▼                     ▼                     ▼
[Servicio Ingestor]    [Motor de Geocercas]   [WebSocket Web]
(Guarda en DB)        (Calcula demoras/Odoo)  (Mapa en vivo)
Desacoplamiento total:
El bus no sabe quién lee el dato ni le importa; solo publica su paquete al broker y queda libre.
Buffer / Colas de retención (Backpressure):
Si tu servidor de Odoo o la base de datos se cae por 5 minutos, el broker acumula los mensajes en memoria/disco en una cola ordenada. Cuando el servidor vuelve a estar en línea, procesa todo el historial acumulado sin perder un solo metro de recorrido.
Distribución 1 a N (
Fan-out
):
Un único mensaje entrante puede ser consumido en paralelo por distintos microservicios a la velocidad que cada uno necesite.

Mínimo (ideal para planes de datos limitados)

El Broker recibe y enruta:
El broker (ej. EMQX o Mosquitto) autentica la unidad por certificado o usuario/contraseña, y pone el mensaje a disposición de los clientes suscritos al patrón
empresa/flota/+/posicion
.
Los Consumidores procesan:
Consumidor A (Geofencing / Reglas):
Un microservicio ligero (en Python o Go) recibe el mensaje, valida si el punto cayó dentro del radio de 30 metros de la parada o cabecera, y si detecta llegada o salida, hace el llamado al endpoint de Odoo que definimos anteriormente (
POST /api/v1/transit/events
).
Consumidor B (Histórico / Big Data):
Escribe el punto directamente en una base temporal o serie de tiempo (TimescaleDB / PostGIS).
Consumidor C (Monitoreo en vivo):
Reenvía por WebSocket al navegador de los despachadores para pintar el colectivo moviéndose en el mapa.
5. ¿Qué broker elegir según el volumen?
Mosquitto / EMQX:
Si tus buses o validadores transmiten directamente vía
MQTT
. EMQX es especialmente potente porque incluye un motor de reglas interno que puede disparar webhooks HTTP directamente sin escribir código intermedio.
RabbitMQ:
Excelente si recibes datos por HTTP o sockets en un ingestor y necesitas colas de trabajo garantizadas con lógica compleja de reintentos y enrutamiento hacia Odoo o bases de datos.
Redis Streams:
Muy rápido, liviano y fácil de levantar en tu mismo
docker-compose.yml
para proyectos medianos (decenas a cientos de buses).

La excepción en la práctica: ¿Quién transmite el dato?
En el transporte público real existen dos escenarios muy distintos:
Escenario 1: El bus transmite directamente a tu servidor (Gana MQTT)
Si controlas el firmware del validador de billetaje, tienes una computadora de a bordo (Raspberry Pi/Linux embebido) o utilizas un rastreador AVL programable (como Teltonika o Suntech que soportan MQTT nativo):
Elección obligatoria:
MQTT
.
Reduces el costo mensual de los planes de datos móviles de la flota y aseguras fluidez en mapas en tiempo real.
Escenario 2: La empresa operadora te entrega los datos vía API de un tercero (Se usa HTTP)
Si los buses ya transmiten a la plataforma del proveedor del GPS o del sistema de billetaje (ej. Geotab, Traccar o el proveedor del validador) y esa empresa te provee a ti la información:
En este caso, la empresa casi siempre entrega un
Webhook HTTP
o una
API REST (JSON)
.
Elección:
Consumir ese
HTTP/Webhook
, pero recibirlo en un microservicio ligero (como FastAPI o Node.js) que actúe de adaptador,
nunca directamente en Odoo
.
Arquitectura óptima para tu solución
El esquema estándar de la industria combina lo mejor de ambos mundos:
[Buses en calle] 
      │ 
      │ (MQTT / binario liviano sobre 4G)
      ▼
[Broker de Mensajería (EMQX / Mosquitto)]
      │
      ├─► [Microservicio Ingestor / Geocercas] (Python / FastAPI)
      │         │
      │         ▼ (HTTP POST solo cuando hay un hito: salida, parada, llegada)
      │   [Odoo ERP] 
      │
      └─► [Mapa en Vivo / Websocket] (Directo al navegador sin tocar Odoo)
Resumen:
Usa
MQTT
del bus al servidor para la transmisión constante de coordenadas (por costo de datos, velocidad y eficiencia). Usa
HTTP (REST)
únicamente para eventos consolidados y comunicación entre tus propios servidores (por ejemplo, del motor de reglas hacia Odoo).
